## 已实现的 Coze 节点

| 节点 | 类型 | 在流程中的职责 |
| --- | --- | --- |
| `Start` | 开始 | 接收 `query` |
| `IntentExtract` | 大模型 | 抽取品类、预算、使用场景与优先项 |
| `NormalizeFields` | 代码 | 统一同义词与金额，输出缺失字段 |
| `RequiredFields` | 条件分支 | 完整需求进入检索；缺失需求进入追问 |
| `ClarifyOneField` | 文本处理 | 一轮只问一个最关键问题 |
| `RetrieveCatalog` | 代码 | 执行品类、预算、库存硬过滤 |
| `HasCandidates` | 条件分支 | 候选为空进入兜底，否则进入排序 |
| `RuleRankV1` | 代码 | 计算五项可解释分数并返回 Top 3 |
| `ReasonGenerate` | 大模型 | 基于商品字段生成适配点、预算关系与取舍 |
| `FactGuard` | 代码 | 校验 ID、价格、差额、限制，阻止库外事实 |
| `NoResultFallback` | 代码 | 计算最低可用价并给出放宽动作 |
| `End` | 结束 | 统一三种状态的响应结构 |

完整变量与分支见 [`../workflow/workflow-spec.md`](../workflow/workflow-spec.md)。

## 实际搭建与验收顺序

1. 新建项目 `智选 Agent｜Coze MVP`，全程保持未部署；
2. 先实现 `Start → NormalizeFields → RequiredFields → ClarifyOneField`，验证追问分支；
3. 将合成商品库作为代码节点常量或项目数据资源接入，不上传任何真实订单或用户数据；
4. 实现硬过滤与 `rule_v1`，以用例 A、C、D 核对候选数和总分；
5. 最后接入理由生成与 `FactGuard`，避免大模型文本掩盖基础逻辑错误；
6. 运行四个固定用例，保存 Coze 原生结果与脱敏截图；
7. 发现初版把 `use_case` 设为软约束后，恢复三字段必填，并将“高性能”归一化为使用场景与优先项；
8. 发现初版含现实或近似现实型号后，将 15 个商品名全部替换为原创中文名称；
9. 记录当前项目视图没有原生单文件导出入口，保留等价配置、项目 ID、版本号与原生证据；
10. 项目继续保持未部署，仅用 GitHub 静态材料供外部查看。

## 大模型节点提示词原则

- **抽取节点**：温度 0，只输出固定 JSON；未知字段用 `null` 或空数组，不推测；
- **理由节点**：温度 0.2，只使用当前 Top 3 的结构化字段；
- 不把大模型用于价格计算、候选过滤、总分或预算差额；
- 所有可确定事实由代码节点覆盖，模型仅负责自然语言表达。

## 预期平台限制与应对

| 可能限制 | 风险 | 应对 |
| --- | --- | --- |
| 原生导出格式随平台版本变化 | GitHub 文件无法直接导入 | 将本 JSON 明确标记为等价配置；原生导出独立保存 |
| 工作流单次调用不保留会话状态 | 追问后不能自动合并上一轮约束 | 由外层 Agent 会话记忆合并，或让用户在下一轮复述完整约束 |
| 大模型节点输出格式漂移 | 理由缺字段或出现库外事实 | JSON 输出 + `FactGuard` 代码节点 + 模板回退 |
| 商品 JSON 作为提示词传入导致 token 增长 | 商品库扩容后成本与延迟上升 | MVP 仅 15 条；正式版改为检索服务或数据库查询 |
| 代码节点浮点与排序实现差异 | 分数末位或同分顺序不同 | 保留完整精度、末端四舍五入、固定 tie-breaker |
